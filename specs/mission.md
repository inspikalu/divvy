# Mission — Divvy

## Problem Statement

Memestocks on Solana have no reason to be held. Once the pump ends, the only
remaining action is to sell. Trading fees accrue to launchpads, LPs, and creators —
never to the people actually holding the bag. At the same time, tokenized equities
(xStock, PreStock, Tessera) exist on-chain but have almost no native use case beyond
being traded like any other SPL token.

Divvy connects the two: it routes a configurable share of a token's trading fees into
a program-owned Dividend Vault, and lets holders claim a pro-rata share as a real
on-chain asset.

## Target User

Two distinct users, both required for the product to function:

1. **Token creator / project team** — launching or already running a token on Meteora
   DBC, looking for a reason for holders to stay. They configure Divvy once.
2. **Token holder** — holds the meme, claims the dividend. Does nothing else.

## Value Proposition

> Divvy is an open dividend layer for Solana memestocks: any Meteora DBC token can opt
> in so that its trading fees are automatically routed to a vault and claimed by
> holders as real tokenized assets.

Short form, as used in the demo: **Hold the meme → earn the stock.**

## Core User Stories

These are the source of truth. Every acceptance criterion in every future
`validation.md` must trace back to one of these stories or to an explicitly approved
stretch goal in this file. A criterion that maps to neither is scope creep and must be
flagged to the project owner, not quietly built.

- **US-1 (Creator, enable)** — As a token creator, I want to enable Divvy on my DBC
  token and set what share of trading fees goes to the Dividend Vault, so that my
  holders have a reason to keep holding after launch.
- **US-2 (Protocol, route)** — As the protocol, I want every relevant trading fee on
  an enabled token to be routed into that token's Dividend Vault automatically, so
  that dividend accrual requires no ongoing action from the creator.
- **US-3 (Holder, see)** — As a holder, I want to see how much dividend I have accrued
  and what the vault holds in total, so that I can verify the yield is real before I
  act on it.
- **US-4 (Holder, claim)** — As a holder, I want to claim my pro-rata share of the
  vault in a single transaction, so that I actually receive the dividend rather than
  just reading about it.
- **US-5 (Anyone, verify)** — As any observer, I want every fee routed and every claim
  paid to be visible as an on-chain transaction I can open in an explorer, so that the
  yield is auditable rather than a number on a dashboard.

## Project Type

**Hackathon / bounty submission** — Stocklana + Meteora DBC bounty. Build window is
**under 48 hours**. Demo environment is **Solana devnet** (approved by project owner;
mainnet is not required).

## Required Deliverables (must-have to qualify)

Ordered by how badly the submission fails without them.

- **RD-1** — A live, working fee → vault → claim flow on a Meteora DBC token. Fees
  generated by real swaps land in a program-owned vault; a holder wallet claims from
  that vault; both steps are real on-chain transactions.
- **RD-2** — A deliberate, non-default Meteora DBC configuration: curve shape and fee
  schedule chosen and justified for a stock-paired quote asset. The bounty asks for
  novel DBC configurations and use cases — a default config disqualifies the core
  claim of the submission.
- **RD-3** — A frontend dashboard showing, for an enabled token: total fees routed,
  current vault balance, the connected wallet's claimable amount, and a working claim
  button.
- **RD-4** — Explorer-verifiable proof: every number shown on the dashboard is backed
  by a transaction signature or account address the judges can open themselves.
- **RD-5** — A 5–7 minute end-to-end demo that runs live, in order: enable → generate
  trading activity → fees land in vault → switch to holder wallet → claim → show
  on-chain proof → explain the DBC configuration.

## Selected Stretch Goals

Approved by the project owner. **Optional**, and gated on the core roadmap's Merge Gate
passing first. Nothing below is allowed to consume time that RD-1 through RD-5 still
need.

- **SG-1 — Loyalty multiplier.** Hold time increases claim weight; selling resets it.
  Rationale: it is what makes the "stickier liquidity" argument true rather than
  asserted, and it is visible in a single screen during the demo.
- **SG-2 — Yield leaderboard.** Ranks enabled tokens by realized yield. Rationale: low
  effort, high visual impact. Only lands if two or more tokens are enabled during the
  demo — if only one token is enabled, skip it rather than shipping a leaderboard with
  one row.

## Explicitly Rejected Scope

Considered and **not** selected. These do not go into `roadmap.md`. If they resurface
mid-build, they need an explicit decision from the project owner first.

- Pyth premium/discount analytics (real equity price vs xStock price).
- Real tokenized stock (PreStock / Tessera) as the settled dividend asset. See
  `resources.md` — devnet has no meaningful tokenized-equity liquidity, so this cannot
  be honestly demonstrated in this build window.
- Push-based distributions. Pull-based claim only.
- Multi-asset dividend baskets.
- Public CLI / SDK for third-party creators.
- Post-graduation DAMM v2 fee continuation as a *working* feature. It may be described
  in the README as designed-for, but it must not be demoed as if it works.
