# Roadmap — Divvy

Implementation order in small phases, sized for a **sub-48-hour** window. Phases are
strictly ordered: each one's Exit Condition must be met before the next begins.

Rough time budget, to be treated as a warning system rather than a schedule. If a phase
runs past roughly double its budget, stop and escalate instead of pushing on.

---

## Phase 0 — Environment & Ground Truth *(~2h)*

Nothing is built yet. This phase exists to kill the project's biggest unknown before
any code depends on it.

- Verify toolchain versions installed match `tech-stack.md` exactly.
- **Confirm Meteora DBC is deployed and usable on devnet.** Record the program ID and
  the resolved SDK version in `tech-stack.md` (Change Log) and any gotchas in Known
  Issues. **If DBC is not usable on devnet, STOP and escalate — this reshapes the
  project, and no later phase should begin.**
- Generate and fund deployer, holder A, holder B wallets. Confirm `.gitignore` covers
  keypairs *before* the first commit.
- Create the devnet dividend-asset SPL mint (also the DBC quote asset).
- Create the tracked addresses file: program IDs, mints, wallets, PDAs.
- Initialize the repo; first commit.

**Exit:** a DBC devnet program ID confirmed by a successful read, three funded wallets,
one mint address, all recorded. Traces to: RD-1, RD-2 (prerequisite).

---

## Phase 1 — Launch a Token on a Deliberate DBC Config *(~5h)*

The bounty's core technical claim. Done early because it is the highest-risk build work.

- Design the curve shape and fee schedule for a stock-paired quote asset. Write down
  the reasoning — the demo requires explaining *why* this config, not just that it exists.
- Launch a token on devnet DBC using that config, with the Phase 0 mint as quote asset.
- Execute real swaps against the curve from the holder wallets.
- Confirm fees accrue where the SDK says they should.

**Exit:** a live devnet DBC token on a non-default, justified config, with real swaps
executed and fees observably accrued. Traces to: RD-2.

---

## Phase 2 — Divvy Program: Config & Vault *(~5h)*

- Anchor program scaffold; deploy to devnet.
- `initialize_config`: stores the token, the fee-share percentage, the dividend mint,
  and excluded wallets.
- Create the program-owned Dividend Vault PDA and its token account.
- Anchor tests for config initialization and the fee-share math.

**Exit:** `anchor test` passes; a config account and vault PDA exist on devnet and are
readable by address. Traces to: US-1, RD-1.

---

## Phase 3 — Fee Routing *(~6h)*

The single most important phase. Nothing in the submission survives this failing.

- Wire DBC-accrued fees into the Dividend Vault at the configured share.
- Route fees generated by Phase 1's swaps; confirm the vault balance increases.
- Record the routing transaction signatures.

**Exit:** a real swap on the Phase 1 token produces a measurable, explorer-verifiable
increase in the vault's token balance. **No stubbing, no manual top-ups.** Traces to:
US-2, RD-1, RD-4.

---

## Phase 4 — Claim *(~5h)*

- Holder snapshot / claim-eligibility state.
- `claim()`: transfers the caller's pro-rata share from the vault; marks it claimed;
  double-claim is rejected.
- Anchor tests for pro-rata math and double-claim rejection.

**Exit:** `anchor test` passes; holder A and holder B each claim from devnet and receive
different, correct amounts; a second claim attempt fails. Traces to: US-4, RD-1.

---

## Phase 5 — Dashboard *(~6h)*

- Next.js app, wallet adapter, connect flow.
- Read and display from chain: total fees routed, vault balance, connected wallet's
  claimable amount.
- Working claim button wired to Phase 4's instruction.
- Every displayed figure links to an explorer address or signature.
- A creator-facing enable/config screen for US-1.

**Exit:** from a fresh browser, connect holder A → see a non-zero claimable amount →
claim → balance updates → every number on screen opens in an explorer. No hardcoded
values anywhere. Traces to: US-1, US-3, US-4, US-5, RD-3, RD-4.

---

## Phase 6 — Merge Gate *(~4h)*

**Everything above must be green before anything below begins.**

- Full end-to-end run from a clean start, following RD-5's demo order exactly.
- Run it **three consecutive times**. A flow that works once is not done.
- Write the reproducible setup script (devnet state can be wiped — recovery must be a
  script, not a rebuild).
- Write the demo script with the explorer links pre-opened.
- Remove debug logging; confirm no secrets are committed; final commit.

**Merge Gate criteria:** RD-1 through RD-5 all demonstrably pass, three runs in a row.

# Stretch Phase *(OPTIONAL)*

**Gated on the Merge Gate above passing.** Do not start any item here until Phase 6 is
complete and committed. Only the two items below are in scope — everything else in
`mission.md`'s Rejected Scope stays out.

Take these in order and stop whenever time runs short. A finished SG-1 beats a
half-finished SG-1 plus a half-finished SG-2.

### SG-1 — Loyalty Multiplier *(~4h)*
Track hold duration; weight claim amount by it; reset on sell. Surface loyalty status on
the dashboard. Requires an Anchor test for the weighted-claim math — this changes the
payout numbers, and wrong numbers in front of judges is the worst available outcome.
**Re-run the full Merge Gate afterward.**

### SG-2 — Yield Leaderboard *(~2h)*
Rank enabled tokens by realized yield. **Skip entirely if only one token is enabled at
demo time** — a one-row leaderboard is worse than no leaderboard. Requires enabling a
second token first, which is itself part of this item's cost.
